Seccion 04 (extra) - Diagnostico: la VM se congela durante la inferencia
Integrantes: Angel Arcos - Sebastian Coral - Juan Orjuela - Javier Rosero | 2026-09-24 | ubuntu-ollama
==================================================================

SINTOMA
  Al ejecutar cualquier modelo (incluso gemma3:1b) la VM deja de responder: el reloj del escritorio
  se detiene, SSH da "Connection timed out during banner exchange" y el boton ACPI se ignora.
  Solo se recupera con reinicio forzado. El journal del arranque anterior se corta en el momento
  de la inferencia (no hay mensajes de OOM ni de "soft lockup": el kernel no alcanza a escribir).

CAUSA RAIZ 1 - VirtualBox corre sobre Hyper-V (NEM), no con VT-x directo
  Log de la VM (VBox.log):
    HM: HMR3Init: Attempting fall back to NEM: VT-x is not available
    NEM:  info: Found optional import WinHvPlatform.dll!...
  Windows 11 tiene activo el hipervisor (Hyper-V / seguridad basada en virtualizacion / WSL2), que
  toma VT-x para si. VirtualBox queda como cliente de la API de Hyper-V (modo "tortuga"), mas lento
  y con problemas conocidos cuando todas las vCPU ejecutan codigo AVX2 intensivo, que es justo lo que
  hace ggml (libggml-cpu-alderlake.so / haswell.so) al multiplicar matrices.

CAUSA RAIZ 2 - sobreasignacion de RAM (ver s02_vm_vs_anfitrion.txt)
  Con 8 GB la VM ademas paginaba en el anfitrion. Se redujo a 6 GB.

EXPERIMENTO: misma consulta corta a gemma3:1b variando los hilos de inferencia (options.num_thread)
  num_thread   resultado                         velocidad de generacion
  1            responde                          5.9 tok/s
  2            responde                          7.2 tok/s
  3            responde                          10.7 tok/s
  4 (defecto)  la VM se congela (3 veces)        -
  Conclusion: el problema aparece cuando la inferencia ocupa las 4 vCPU a la vez.

SOLUCION APLICADA (administracion con systemd + cgroups v2)
  /etc/systemd/system/ollama.service.d/limites.conf
    [Service]
    Environment="OLLAMA_MAX_LOADED_MODELS=1"   # un solo modelo en RAM
    Environment="OLLAMA_NUM_PARALLEL=1"        # una peticion a la vez
    AllowedCPUs=0-2                            # cpuset del cgroup: la vCPU 3 queda para kernel/sshd/GNOME
  $ systemctl show ollama -p AllowedCPUs   -> AllowedCPUs=0-2
  $ taskset -cp <PID de ollama serve>       -> lista de afinidad actual: 0-2
  Ademas PARAMETER num_thread 3 en el Modelfile (y "num_thread": 3 en las llamadas a la API).

  Por que las dos cosas: solo con AllowedCPUs, Ollama sigue lanzando 4 hilos (cuenta los nucleos de
  /proc/cpuinfo) sobre 3 CPU. Los hilos de ggml esperan en barreras con espera activa (spin), asi que
  la sobresuscripcion hunde el rendimiento: el procesamiento del prompt cayo a 5.6 tokens/s con el
  proceso al 283 % de CPU. Con 3 hilos en 3 CPU no hay sobresuscripcion y la VM sigue respondiendo.

SOLUCION DE FONDO (requiere decision del dueno del equipo y reiniciar Windows)
  Desactivar el hipervisor de Windows para que VirtualBox use VT-x directo:
    bcdedit /set hypervisorlaunchtype off   (+ desactivar "Integridad de memoria" en Seguridad de Windows)
  Contra: deja de funcionar WSL2 / Docker Desktop / Sandbox mientras este desactivado.
